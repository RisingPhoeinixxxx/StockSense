Internal Engineering Documentation

StockSense Inventory Management System

A production-oriented, real-time, multi-user inventory management platform built on Vite, React, TypeScript and Supabase — covering product catalogues, warehouses, stock movements, and a fully audited operations ledger.

Status: Active Version 1.0.0 Frontend: React 18 + Vite Backend: Supabase (Postgres · Auth · Realtime)

Section 01

Executive Overview

StockSense is a single-page inventory management application designed for a small-to-mid-size operation running one or more warehouses. It replaces spreadsheet-based stock tracking with a live, shared, multi-user workspace where every stock movement is validated through a formal operation (Receipt, Delivery, Internal Transfer, or Adjustment) and permanently recorded in an append-only ledger.

01

Real Authentication

Backed entirely by Supabase Auth — email/password sign-up, sign-in, and secure password recovery. No demo or fallback login path exists.

02

Shared Live Workspace

All authenticated users read and write one shared inventory workspace (app_states.id = 'default'), synchronized instantly via Supabase Realtime.

03

Private Profiles

Each user has a private profile row protected by Postgres Row-Level Security — one user can never read or modify another's profile.

04

Auditable Ledger

Every completed operation writes an immutable entry to a stock ledger: what moved, from where, to where, how much, and who performed it.

Who this document is for Engineers onboarding onto the codebase, reviewers auditing the data flow and security model, and operators planning a Supabase deployment.

Section 02

System Architecture

StockSense is a client-heavy single-page application. There is no custom backend server — Supabase serves as the entire backend surface: authentication, relational storage, row-level security enforcement, and realtime change propagation.

Design Principles

  • Client-authoritative UI, server-authoritative truth. The UI updates optimistically from local state, but the shared workspace row in Postgres is the single source of truth once a user is authenticated.
  • Offline-tolerant caching. Application state is mirrored to localStorage per user ID, so the dashboard renders instantly on reload before the cloud round-trip completes.
  • No custom API layer. All reads/writes go directly from the browser to Supabase using the anonymous (publishable) key; authorization is enforced entirely by Postgres RLS policies, not application code.
  • Eventual consistency via Realtime. Concurrent users converge on the same state through Postgres change events rather than polling.

Authentication & Session Flow

Authentication is handled exclusively by Supabase Auth (src/pages/Auth.tsx). There is no local or demo credential path — if Supabase environment variables are missing, every auth action fails with an explicit configuration error rather than silently granting access.

Password Recovery Detail

When Supabase redirects the user back with a recovery token in the URL hash, App.tsx detects type=recovery on mount and forces the Auth component into forgot mode with recoveryMode set — presenting a "Set New Password" form instead of the usual reset-request form.

Configuration requirement The exact origins used locally and in production (e.g. http://localhost:5173 and the production domain) must be registered under Authentication → URL Configuration in the Supabase dashboard, or recovery links will fail to redirect correctly.

Section 08

Inventory Operations Engine

All stock-affecting logic lives in a small set of pure-ish functions in src/pages/Pages.tsx: completeReceipt, completeDelivery, completeTransfer, and completeAdjustment. Each mutates a cloned draft of AppState (via structuredClone), applies inventory deltas, appends one or more ledger entries, and flips the document's status to Done.

Draft Waiting Ready Done Canceled

Section 09

State Management & Realtime Sync

StockSense layers a fast local cache underneath a slower, authoritative cloud store, reconciled automatically through effects in App.tsx.

9.1 Local Persistence

src/lib/store.ts seeds a demo dataset (seed()) and persists AppState to localStorage under a per-user key (stocksense_state_v2_<userId>), so the UI has something to render instantly before any network round trip resolves.

9.2 Cloud Read / Write

src/lib/cloudStore.ts wraps four Supabase interactions: fetching the shared state row, upserting it, subscribing to Postgres change events on app_states, and fetching/updating a user's private profiles row.

Figure 9.1 — Local Save & Debounced Cloud Push

flowchart TD
    A["AppState changes (any action)"] --> B["save(state, userId) → localStorage"]
    B --> C{"skipNextCloudPush flag set?"}
    C -- "true (state came from cloud/realtime)" --> D["Clear flag — do not re-push"]
    C -- false --> E{"authed AND Supabase configured AND cloudReady?"}
    E -- No --> F["No cloud push"]
    E -- Yes --> G["Debounce 250ms"]
    G --> H["pushCloudState(state, userId)
upsert app_states id='default'"]

Figure 9.2 — Multi-User Realtime Propagation

sequenceDiagram
    participant A as User A (browser)
    participant DB as Supabase Postgres
    participant RT as Realtime Channel
    participant B as User B (browser)
    A->>DB: upsert app_states (id='default', state)
    DB-->>RT: postgres_changes event (UPDATE)
    RT-->>A: broadcast (skipped — A is the author)
    RT-->>B: broadcast change
    B->>B: skipNextCloudPush = true; setState(next)
    B->>B: UI re-renders with A's changes, no re-push loop
Why the skip flag exists Without skipNextCloudPush, receiving a remote update would trigger the local save effect, which would immediately re-push the same state back to Supabase — creating a redundant write (and, with two active clients, a feedback loop).

Database Schema & Row-Level Security

The full schema lives in supabase/schema.sql and is idempotent — it can be re-run safely against an existing project.

10.3 Automation

  • Trigger on_auth_user_created calls handle_new_user() after every insert into auth.users, upserting a matching profiles row (preserving any already-set full_name).
  • Realtime publication: the script adds app_states and profiles to the supabase_realtime publication if not already present, so client subscriptions can receive change events.
  • Legacy row migration: the script clears user_id on the id='default' row so pre-existing per-user policies don't block shared access after an upgrade.
Security note The published RLS model treats the workspace as fully shared and mutually trusted: any authenticated user can read and write the entire inventory. There is currently no per-user write scoping, role gating, or field-level permission inside app_states — this is a single shared team workspace by design, not a multi-tenant system.

Section 11

Setup & Deployment Guide

11.1 Provision Supabase

  1. Create (or open) a Supabase project.
  2. Open SQL Editor, paste the full contents of supabase/schema.sql, and run it once.
  3. Under Authentication → URL Configuration, add every origin the app will run from (local dev and each production domain).

11.2 Local Development

Create a .env file beside package.json:

VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY
npm install
npm run dev
Never do this Never place the Supabase service_role/secret key in .env or in any frontend build — it bypasses Row-Level Security entirely. Only the publishable/anon key belongs in a Vite VITE_* variable.

11.3 Production (Vercel / Netlify)

  • Add VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY as environment variables on the hosting project.
  • Vite injects VITE_* variables at build time — changing them requires a fresh build and redeploy, not just a restart.
  • Build command: tsc -b && vite build (defined in package.json).

11.4 Troubleshooting: "Supabase is not configured"

  • Confirm .env sits directly beside package.json.
  • Confirm both variable names begin with VITE_ exactly.
  • Restart the Vite dev server after any .env edit.
  • For a deployed build, confirm the hosting provider's environment variables are set and trigger a redeploy.

Section 12

Security Considerations

Enforced today
  • Real Supabase Auth — no demo/local bypass
  • Profiles isolated per user via RLS
  • Only the anon/publishable key ships to the browser
  • Delivery/Transfer validation blocks negative stock
  • Ledger entries are append-only from application code
Worth revisiting
  • Any authenticated user can write the entire shared workspace — no per-role permissions
  • No server-side validation layer independent of the client (all business rules run in the browser)
  • No optimistic-concurrency / conflict resolution beyond last-write-wins on app_states
  • Ledger writes are not protected by a database-level trigger, only by application convention

Section 13

Known Limitations & Roadmap Candidates

  • Single shared workspace only — multi-team/multi-tenant support would require a workspace ID model instead of a hardcoded 'default' row.
  • Draft/Canceled states unreachable from the UI — the type system supports them but no action currently transitions a document into either.
  • No role-based access control — the role field on Profile is descriptive only; it does not currently gate any action.
  • No server-side business-rule enforcement — a malicious client with valid auth could bypass client-side stock checks by writing directly to app_states (mitigated only by trusting the workspace's members).
  • Add/Edit forms for Warehouses and Locations are minimal — no validation beyond required text fields.
